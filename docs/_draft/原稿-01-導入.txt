## 0-1 このドキュメントは何か

「パイレーツ・ポッパーズ(海賊の秘宝)」は、画面上のレールを流れてくる玉の列に、
下の大砲から玉を撃ち込み、同じ色を3個以上つなげて消していくパズルゲームです。
Zuma や Luxor と同じジャンルで、原作は PlayFirst の Pirate Poppers(2006)。

このドキュメントは **そのゲームのソースコードを、上から順に読めるようにするための解説書**
です。プロジェクトにすでにある README.md は「どんなゲームか / なぜそう設計したか」を
説明していますが、こちらは「**そのコードがどう動いているか**」だけを説明します。

対象読者はプログラミング初心者です。専門用語は出てきたその場で説明します。


## 0-2 まず動かしてみる

ビルドもインストールも要りません。

  1. リポジトリのルートにある index.html をダブルクリックする
  2. ブラウザが開いて「🏴‍☠️ 海賊の秘宝」というタイトルが出る
  3. 音楽の読み込みが終わったら画面をクリックすると始まる

操作は3つだけです。

  ・マウスを左右に動かす → 大砲が横に動く
  ・クリック             → 真上に玉を撃つ
  ・右クリック or Space   → 今の玉と次の玉を入れ替える

デバッグ用の入り口も覚えておくと、あとの章で実験しやすくなります。

  index.html?level=3      レベル3から始める(= コース2「橋を渡る道」を見る)
  index.html?level=7      レベル7から始める(= コース4「四叉の激流」4レーン)
  index.html?editcourse=1 コースエディタを直接開く

なぜレベルでコースが変わるのか、どこで決まっているのかは章12で扱います。


## 0-3 ファイルの並び

  pirate_poppers/
    index.html        ← 唯一の HTML。CreateJS を CDN から読み、js/ を順に読む
    js/               ← ゲーム本体。16 個の .js、合計およそ 7,300 行
    BGM/  SE/         ← 音源(mp3)

js/ の中身は、**index.html に書かれている読み込み順そのものが依存関係の順** です。

  background  → 背景の海
  audio       → 音
  rail        → 道の幾何
  ball        → 玉の絵と色の抽選
  fx          → パーティクル等の演出
  chain       → 玉の列の物理(このゲームの心臓)
  powerups    → 落ちてくるアイテム

  hud         → 画面上部の情報表示
  crisis      → 危機の演出

たとえば rail.js は chain.js の存在を知りませんが、chain.js は rail を使います。

## 0-5 このドキュメントでの言葉の約束

コードを読むときに一番つまずくのは「同じものを別の名前で呼ばれること」です。
本ドキュメントでは次のように統一します。コード側の名前も併記します。

  玉        … 画面上の丸い球。コードでは ball / balls
  チェーン   … レール上に並んだ玉の列全体
  グループ   … チェーンのうち、隙間なくくっついている連続部分
  レーン     … 「レール1本 + そのチェーン + その樽」の1組。コードでは lane
  コース     … レーンの集まり。コードでは course
  レール     … 道1本ぶんの幾何情報。コードでは rail
  弧長 d     … レール上を洞窟から測った距離(単位 px)。玉が持つ唯一の位置
  洞窟       … d = 0 の地点。玉が湧いてくる穴
  樽         … レールの終点。玉が入るとゲームオーバーに近づく
  波(wave) … 一度にまとめて補給される玉の一団
  宝玉       … 波の末尾に付く金色の玉
  レイヤー   … 描画の重なり順を作る箱。コードでは createjs.Container
  tick       … 1フレーム。だいたい 1/60 秒
  dt         … 1フレームの経過秒数。だいたい 0.0167

## 1-1 このゲームで起きていることを一言で

  「レールという1本の線があり、玉はその線上の距離 d だけを持つ。
   毎フレーム d を増やし、d から画面の座標を計算して絵を置く。」

これが全部です。ゲームの複雑さのほとんどは、この「d をどう増やすか」
「d が近づいたらどうするか」の規則にあります。

なぜ (x, y) ではなく距離 d で持つのか。理由は3つあります。

  1. 玉が曲がりくねった道を進むとき、(x, y) を直接動かすのは難しい。
     d を増やすだけなら、道がどんな形でも「進む」が1行で書ける。
  2. 玉どうしの前後関係が「d の大小」だけで決まる。
     画面上でどんなに折り返していても、d が大きい玉が後ろ、小さい玉が前。
  3. 「玉2個ぶん離れている」が |d1 - d2| = 48 と書ける。
     直線距離だと、カーブの内側と外側でずれてしまう。

この「1次元に押し込む」発想が、このゲームのコード全体を貫いています。


## 1-2 状態機械(ゲームがいまどのモードか)

PP.game.state という1つの文字列が、ゲーム全体のモードを表します。
コードのあちこちで `if (g.state !== "playing") return;` と書かれているのは、
「プレイ中でなければ何もしない」という意味です。

  "loading"   音源を読み込み中。クリックを受け付けない
  "title"     タイトル表示中。クリックで開始
  "playing"   プレイ中。ここだけが物理を動かす
  "clear"     レベルクリア。クリックで次のレベル
  "draining"  ゲームオーバー演出中(玉が樽へ吸い込まれている)。クリック不可
  "over"      ゲームオーバー確定。クリックでリスタート

遷移はすべて main.js の onStageDown()(クリック)と、
tick() の中の判定で起きます。

  loading ─(音源読了)→ title ─(クリック)→ playing
  playing ─(全滅)   → draining ─(演出終了)→ over ─(クリック)→ playing
  playing ─(掃討完了)→ clear ─(クリック)→ playing(レベル+1)

## 1-3 1フレームの旅

ブラウザは1秒間に約60回、画面を描き直します。CreateJS の Ticker がその
タイミングで main.js の tick(e) を呼びます。tick が1回走ると何が起きるのか、
順番に見ていきます。

  js/main.js:183 の tick(e) より

  ① dt を求める       e.delta(ミリ秒)を秒に直し、0.05 秒で頭打ちにする
  ② コンボタイマー減算  1.6 秒たったらコンボ倍率をリセット
  ③ PP.chain.update    全レーンのチェーンを1フレーム進める(章06〜08)
  ④ PP.cannon.updateShots 飛んでいる玉を進め、当たったら割り込ませる(章09)
  ⑤ PP.powerups.update  落下アイテムを進め、大砲に触れたら発動(章11)
  ⑥ PP.hud.updateEffects HUD の効果アイコンの残り秒を更新
  ⑦ 死亡判定           どれかのレーンで玉が樽に3個入ったらゲームオーバー
  ⑧ 生存ゲージ減算      時間切れなら掃討フェーズへ
  ⑨ クリア判定         掃討中で全レーンが空ならクリア
  ⑩ PP.crisis.update   危機の演出(赤い帳・心拍)
  ⑪ PP.cannon.syncColors 装填色が盤面から消えていたら引き直す
  ⑫ PP.bg.update       背景の海を動かす
  ⑬ PP.courseView.updateRailFlow 溝を流れる光を動かす
  ⑭ PP.fx.updateShake  画面の揺れ
  ⑮ PP.cannon.updateAim 照準ガイドを引き直す
  ⑯ renderChains()     ★ すべての玉の d を画面座標に変換して view を置く
  ⑰ stage.update(e)    ★ CreateJS に「描け」と命じる

重要なのは ⑯ と ⑰ の関係です。

  ⑯ までは **数値をいじっているだけ** で、画面は1ピクセルも変わりません。
  ⑰ の stage.update() が呼ばれてはじめて、canvas が描き直されます。

初心者がよく誤解するところです。b.view.x = 100 と書いても画面は変わりません。
「次に stage.update() が呼ばれたときに、そこに描かれる」という予約にすぎません。

【GIF: createjs/ticker-loop.gif】
  tick の①〜⑰が上から順に点灯し、⑯⑰のところで画面が更新されるのが見える。
  あわせて dt = min(delta/1000, 0.05) のクランプ(フレーム落ち時の暴走防止)も。


## 1-4 dt を 0.05 で頭打ちにする理由

  js/main.js:184
    var dt = Math.min(e.delta / 1000, 0.05);

e.delta は「前のフレームからの経過ミリ秒」です。普通は 16〜17 ですが、
タブを別ウィンドウに切り替えて戻ってきたときなどは 3000(3秒)になることもあります。

もしそのまま使うと:

  玉の移動距離 = 速度 600 px/s × 3 秒 = 1800 px

1フレームで玉が 1800px 飛びます。玉の直径は 48px なので、当たり判定も
重なり解消も全部すり抜けて、チェーンがぐちゃぐちゃになります。

0.05 秒(= 20fps 相当)で頭打ちにすると、最悪でも 600 × 0.05 = 30px。
玉の半径 24px より少し大きい程度なので、破綻しません。

「時間ベースの物理では、dt に上限を付ける」— これは一般的な鉄則です。


## 1-5 データの流れ

だれがだれのデータを読み書きするのか。矢印は「読む/呼ぶ」向きです。

                       ┌─────────────┐
                       │  PP.game    │ ← 共有状態(全員がここを見る)
                       │  score      │
                       │  lanes[]    │
                       │  effects    │
                       └──────┬──────┘
                              │
        ┌────────┬────────────┼────────────┬─────────┐
        │        │            │            │         │
     chain     cannon      powerups       hud      crisis
        │        │            │
        │        └─→ chain.insertShot() で玉を割り込ませる
        │
        └─→ rail.posAt(d) で座標を得る
            ball.makeView() で絵を作る
            fx.particles() で演出
            audio.pop() で音

PP.game は「みんなが書き込める黒板」です。行儀のよい設計かというと議論の
余地はありますが、ファイル間の受け渡しが単純になり、`file://` で開くだけで
動くという要件(ES Modules を使わない)と相性がよい構造です。

各レーンの中身は次のようになっています(js/config.js:393 のコメントより)。

  lane = {
    rail,           このレーン専用のレール幾何(rail.create が返す)
    balls: [],      このレーンのチェーン。balls[0] が先頭(樽に一番近い)
    recoil: null,   反動の状態
    wave, pending, needTreasure, waveFresh, waveTimer,   波の補給状態
    pendingMatches, 割り込みアニメ完了後に判定する予約
    barrel          この樽の表示パーツ
  }

そして玉1個は、驚くほど小さなオブジェクトです。

  通常の玉 { d, color, wave, view, pull, slide, ins }
  宝玉     { d, color: null, treasure: true, wave, view, pull, slide }

  d      レール上の距離(これが位置のすべて)
  color  0〜5 の色番号(PP.PALETTE の添字)
  wave   何波目に生まれたか(宝玉の粉砕判定に使う)
  view   画面に出す CreateJS の表示オブジェクト
  pull   磁力で巻き戻っている速度
  slide  押し広げられた表示上のずれ
  ins    割り込みの滑り込みアニメの状態


## 1-6 ちょっと変わった書き方: IIFE

すべての js ファイルは、こういう形で始まって終わります。

  (function () {
    "use strict";
    var PP = window.PP;
    ...
    PP.chain = { update: update, ... };
  })();

この `(function () { ... })();` は **IIFE(即時実行関数式)** と呼ばれます。
「関数を作って、その場ですぐ呼ぶ」という書き方です。

なぜこうするのか。**変数を外に漏らさないため** です。

もし IIFE を使わずに

  var D = PP.D;        // chain.js のつもりで書いた

とファイルの一番外側に書くと、これは「グローバル変数」になります。
別のファイルでも同じ名前 D を使っていたら、上書きされて壊れます。
16個のファイルがあるので、事故は確実に起きます。

IIFE の中に書けば、その変数は関数の中だけのもの(ローカル変数)になり、
外からは見えません。そして外に見せたいものだけを

  PP.chain = { update: update };

と、PP という1つの入れ物に入れて公開します。これを **名前空間** と呼びます。
このゲームの名前空間は PP(Pirate Poppers)ひとつだけです。

`"use strict"` は「厳格モード」の宣言で、うっかりミスをエラーにしてくれます。
たとえば var を書き忘れて `x = 5` とすると、通常はグローバル変数が勝手に
作られてしまいますが、厳格モードではエラーになります。

## 2-1 CreateJS とは

HTML の <canvas> は「絵を描ける四角い領域」ですが、生の canvas API はとても原始的です。

  ctx.beginPath();
  ctx.arc(100, 200, 24, 0, Math.PI * 2);
  ctx.fillStyle = "#e01810";
  ctx.fill();

これで赤い円が1つ描けます。でも「その円を後で動かす」ことはできません。
canvas は絵の具と同じで、塗ったら塗りっぱなし。動かしたければ全部消して
描き直すしかありません。

CreateJS(その中の EaselJS)は、この面倒を引き受けてくれるライブラリです。

  ・画面に出したいものを **オブジェクト** として持っておく
  ・オブジェクトには x, y, rotation, scaleX, alpha などの property がある
  ・stage.update() を呼ぶと、canvas を全部消して、全オブジェクトを描き直す

つまり「絵を描く」から「物を置く」へ考え方が変わります。これを
**表示リスト(display list)** といいます。Flash を触ったことがある人には
おなじみの構造で、CreateJS はもともと Flash の考え方を JavaScript に
持ってきたライブラリです。

index.html:170 で CDN から読み込んでいます。

  <script src="https://code.createjs.com/1.0.0/createjs.min.js"></script>

このファイルには EaselJS(表示)、TweenJS(アニメーション)、
SoundJS、PreloadJS が全部入っています。このゲームが使うのは EaselJS と
TweenJS の2つだけです。


## 2-2 Stage — 舞台

  js/main.js:348
    stage = PP.stage = new createjs.Stage("gameCanvas");

"gameCanvas" は index.html の <canvas id="gameCanvas"> の id です。
Stage は「この canvas を私が管理します」という宣言で、表示リストの根っこです。

Stage にできる大事なことは2つ。

  stage.addChild(何か)   舞台に物を乗せる
  stage.update()         いま乗っている物を全部 canvas に描き直す

stage.update() を呼ばない限り、画面は絶対に変わりません。
このゲームでは main.js:235 の tick の最後で1回だけ呼んでいます。


## 2-3 Container — 箱

  js/main.js:360
    path: new createjs.Container(),

Container は「物をまとめて入れる箱」です。箱自体は何も描きませんが、

  ・箱に入れた物は、まとめて動かせる(箱の x を変えれば中身も全部動く)
  ・箱の順番が、そのまま描く順番になる(= 重なり順)

このゲームは、この「重なり順」のために Container を 16 個作っています。

  js/main.js:359-376
    PP.layers = {
      path:        道の絵
      railFlow:    溝を流れる光
      bridgeUnder: 橋の落ち影・アーチ・橋脚
      ballUnder:   橋の下を通る玉
      bridge:      橋の桁(これが下の玉を隠す)
      ballOver:    橋の上を通る玉
      tunnel:      トンネルの覆い(これが中の玉を隠す)
      barrel:      樽の手前側
      shot:        飛んでいる玉
      item:        落ちてくるアイテム
      fx:          パーティクル
      cannon:      大砲
      crisis:      危機の赤い帳
      doom:        ゲームオーバーの暗幕
      hud:         画面上部の情報
      overlay:     タイトル/結果のパネル
    };

  js/main.js:377-381
    stage.addChild(PP.layers.path, PP.layers.railFlow, PP.layers.bridgeUnder,
      PP.layers.ballUnder, PP.layers.bridge, PP.layers.ballOver,
      PP.layers.tunnel, PP.layers.barrel,
      PP.layers.shot, PP.layers.item, PP.layers.fx, PP.layers.cannon,
      PP.layers.crisis, PP.layers.doom, PP.layers.hud, PP.layers.overlay);

**先に addChild したものが奥、後のものが手前** です。
だから path(道)が一番奥で、overlay(結果パネル)が一番手前になります。

この順番には全部理由があります。特に面白いのが橋まわりです。

  bridgeUnder(影・アーチ) → ballUnder(下の玉) → bridge(桁) → ballOver(上の玉)

「桁」が下の玉と上の玉の**間**にあるので、下を通る玉は桁に隠れ、
上を通る玉は桁の上に見えます。これだけで立体交差が成立します。

なお main.js:355-358 のコメントには、bridgeUnder を path と分けた理由も
書かれています。橋の影を path に描いてしまうと、あとから描かれる別レーンの道が
影を上塗りしてしまい、橋が浮いて見えなくなるからです。

【GIF: createjs/layer-stack.gif】
  16 レイヤーが奥行き方向に分解して並び、玉が bridge をまたぐときに
  ballUnder → ballOver へ移動する様子が見える。

また、当たり判定に関係ない層はマウスイベントを切っています。

  js/main.js:382-388
    PP.layers.railFlow.mouseEnabled = false;
    PP.layers.bridgeUnder.mouseEnabled = false;
    ...

mouseEnabled = false にすると、CreateJS はマウス座標がどのオブジェクトの上に
あるかを調べるとき、その層を丸ごと飛ばします。この判定は毎フレーム走るので、
飾りの層を切っておくと地味に効きます。


## 2-4 Shape と Graphics — 図形

  var s = new createjs.Shape();
  s.graphics.beginFill("#e01810").drawCircle(0, 0, 24);

Shape は「図形1個」を表す表示オブジェクトです。中身の描き方は
s.graphics に命令を積んでいきます。

Graphics の命令はメソッドチェーンで書きます。ポイントは
**「色を決めてから形を描く」** という順番です。

  beginFill(色)          これから描く形をこの色で塗る、と宣言
  beginStroke(色)        これから描く形の輪郭をこの色にする、と宣言
  setStrokeStyle(太さ)   輪郭の太さ
  drawCircle(x, y, r)    円
  drawRect(x,y,w,h)      四角
  drawRoundRect(...)     角丸四角
  drawEllipse(...)       楕円
  moveTo / lineTo        折れ線
  quadraticCurveTo       二次ベジェ曲線
  arc(x,y,r,a0,a1)       円弧
  endStroke()            輪郭の宣言を終える
  clear()                全部消す

順番を間違えるとよくある事故が起きます。

  ✗ s.graphics.drawCircle(0,0,24).beginFill("#f00");   → 何も描かれない
  ○ s.graphics.beginFill("#f00").drawCircle(0,0,24);   → 赤い円

【GIF: createjs/graphics-order.gif】
  beginFill → drawCircle → beginStroke → drawCircle の各段階で
  絵がどう積み上がるかを1コマずつ見せる。

このゲームは画像ファイルを1枚も使っていません。玉も、大砲も、樽も、
背景の海も、全部この Graphics 命令で描いています。
たとえば玉の下地は radial gradient(放射状グラデーション)です。

  js/ball.js:63-67
    body.graphics
      .beginRadialGradientFill([p.light, p.main, p.main, p.dark, p.edge],
        [0, 0.26, 0.58, 0.88, 1],
        -R * 0.32, -R * 0.34, R * 0.06, 0, 0, R)
      .drawCircle(0, 0, R);

  第1引数 色の配列
  第2引数 各色の位置(0〜1)
  第3〜5  内側の円(中心x, 中心y, 半径)
  第6〜8  外側の円(中心x, 中心y, 半径)

内側の円を左上(-R*0.32, -R*0.34)にずらしているので、左上から光が
当たっているように見えます。


## 2-5 座標系と registration point

CreateJS の座標は「左上が (0,0)、右が +x、下が +y」です。
数学の授業と違って **y は下向きが正** なので注意してください。

各表示オブジェクトの x, y は「親から見た自分の位置」です。
そして「自分のどこを基準に置くか」は regX, regY で決まります。

  js/ball.js:48-51
    function sprite(canvas) {
      var b = new createjs.Bitmap(canvas);
      b.regX = b.regY = CB;
      return b;
    }

CB は R + 2 = 26 です。Bitmap は本来「左上を基準に置く」ものですが、
regX/regY を画像の中心にずらすことで「中心を基準に置く」ようにしています。

これをやっておかないと、b.rotation を変えたときに左上を軸にぐるぐる回って
しまいます。玉は中心を軸に回ってほしいので、regX/regY の設定が必須です。


## 2-6 Ticker — 時計

  js/main.js:441-442
    createjs.Ticker.timingMode = createjs.Ticker.RAF;
    createjs.Ticker.on("tick", tick);

Ticker は「一定間隔で関数を呼んでくれる時計」です。

timingMode に RAF を指定すると、内部で requestAnimationFrame を使います。
これはブラウザが「次に画面を描き直すよ」というタイミングで呼んでくれる仕組みで、

  ・モニタのリフレッシュレートに同期する(普通は 60fps)
  ・タブが非表示のときは呼ばれない(バッテリーを無駄にしない)

という性質があります。setInterval(fn, 16) より正確で行儀がよい方法です。

on("tick", tick) で登録した関数には、イベントオブジェクト e が渡されます。
このゲームが使うのは e.delta(前フレームからの経過ミリ秒)だけです。

  js/main.js:184
    var dt = Math.min(e.delta / 1000, 0.05);

そして最後に stage.update(e) と、e をそのまま渡しています。

  js/main.js:235
    stage.update(e);

これは「この tick イベントを、ステージ上の子オブジェクトにも伝えて」という意味で、
Sprite(スプライトシートのアニメーション)を使っているときに必要になります。
このゲームは Sprite を使っていないので実質どちらでも同じですが、作法として正しい形です。


## 2-7 Tween — アニメーション

毎フレーム自分で数値を進めるのが「物理」なら、
「0.3秒かけて大きさを 1.35 倍にして、そのあと 0.1 秒でゼロにする」のような
時間指定の動きは Tween(TweenJS)に任せます。

玉が消えるときの演出を見てみましょう。

  js/chain.js:629-633
    createjs.Tween.get(b.view, { override: true })
      .wait(k * 15)
      .to({ scaleX: 1.35, scaleY: 1.35 }, 60)
      .to({ scaleX: 0, scaleY: 0, alpha: 0 }, 100, createjs.Ease.backIn)
      .call(function () { if (b.view.parent) b.view.parent.removeChild(b.view); });

  Tween.get(対象)   この表示オブジェクトを動かす Tween を作る
  { override: true } 同じ対象に前の Tween が残っていたら、それを捨てる
  .wait(ミリ秒)     何もしないで待つ
  .to({...}, 時間, イージング) プロパティをその値まで変化させる
  .call(関数)       そこまで来たら関数を呼ぶ

これらは **数珠つなぎ(チェーン)で順番に実行** されます。
上の例は「k*15 ミリ秒待つ → 60ms で 1.35 倍に膨らむ → 100ms で消える → 削除」。

k は消える玉の並び順(0,1,2,...)なので、k*15 ミリ秒ずつずらすことで
玉が左から順にパパパッと弾ける演出になります。

override: true が大事です。これがないと、同じ玉に対して以前かけた Tween が
残っていて、2つの Tween が同じ scaleX を奪い合ってガタガタになります。

イージングは「変化のしかた」です。

  Ease.linear    等速。機械的
  Ease.quadOut   最初速く、だんだん遅く。自然に止まる
  Ease.quadIn    最初遅く、だんだん速く。落下・吸い込み
  Ease.backOut   目標を少し行き過ぎてから戻る。「ポンッ」と出る感じ
  Ease.backIn    逆に少し引いてから飛び出す。「タメ」がある

【GIF: createjs/tween-ease.gif】
  同じ距離を linear / quadOut / backOut / backIn の4本が同時に走り、
  到達タイミングと行き過ぎの違いが見える。

Tween は Ticker に自動で登録されるので、自分で update を呼ぶ必要はありません。
逆に「もう要らない Tween」を放置すると動き続けるので、

  js/chain.js:535
    createjs.Tween.removeTweens(t.view.glow);

のように明示的に止める場面があります(宝玉の光るループ Tween)。


## 2-8 cache — 焼き込み

これがこのゲームで一番効いている最適化です。

問題: Graphics で描いた図形は、stage.update() のたびに
**毎回ゼロから計算し直されます**。放射状グラデーションの円を1個描くのは
そこそこ重い処理で、玉が 100 個あれば毎フレーム 100 回それをやります。

解決: 一度だけ描いて、その結果を画像として取っておく。これが cache です。

  js/ball.js:41-44
    function bake(disp) {
      disp.cache(-CB, -CB, CS, CS);
      return disp.cacheCanvas;
    }

  disp.cache(x, y, 幅, 高さ)

を呼ぶと、CreateJS は裏で見えない canvas を作り、そこにその表示オブジェクトを
1回だけ描いて、以後は「その canvas を1枚貼るだけ」に切り替えます。
描いた結果は disp.cacheCanvas から取り出せます。

このゲームはさらに一歩進んでいて、**色ごとに1回だけ焼いて、全部の玉で使い回して**
います。

  js/ball.js:125-136
    function makeView(colorIndex) {
      if (baseCanvas[colorIndex] === undefined) bakeColor(colorIndex);
      if (!spinCanvas) bakeSpin();

      var cont = new createjs.Container();
      cont.addChild(sprite(baseCanvas[colorIndex]));   // 下地+リム+フレネル
      var spin = sprite(spinCanvas);                   // 回転する塗装の合わせ目
      cont.addChild(spin);
      cont.addChild(sprite(shadeCanvas[colorIndex]));  // 陰影・スペキュラ・輪郭
      cont.spin = spin;
      return cont;
    }

赤い玉が 30 個あっても、焼いた canvas は赤ぶんの1枚だけ。
30 個の Bitmap がその同じ canvas を参照します。メモリも描画時間も1/30 です。

【GIF: createjs/cache-bake.gif】
  左: cache なし = 毎フレーム 100 個ぶんのグラデーションを再計算
  右: cache あり = 1回焼いて、あとは Bitmap を貼るだけ
  フレームごとの処理量の差が棒グラフで見える。

さらに ball.js の冒頭コメント(js/ball.js:19-35)には、
「重ならないレイヤーは1枚に焼き込んでも見え方が変わらない」という考察があります。

  従来: body → spin → rim → fres → shade  の5枚
  現在: base(body+rim+fres を焼き込み) → spin → shade  の3枚

spin は内側(半径の 0.72 倍まで)にしか描かれず、rim/fres は縁(半径 -2.7 以内)
にしか描かれないので、両者は絶対に重なりません。だから body・rim・fres を
1枚にまとめても、spin より下にあるという関係は保たれる、という理屈です。

【注意】cache には落とし穴もあります。

  ・cache した後に graphics を書き換えても、画面は変わりません。
    updateCache() を呼ぶ必要があります。
  ・cache 領域からはみ出た部分は切り落とされます。上の CB = R + 2 の
    「+2」は、輪郭線が欠けないための余白です。


## 2-9 マウス入力

  js/main.js:419-421
    stage.on("stagemousedown", onStageDown);
    stage.on("stagemousemove", function (e) {
      PP.cannon.setX(e.stageX);
    });

"stagemousedown" / "stagemousemove" は Stage 全体で発火するイベントです。
個々のオブジェクトに付けるのではなく、舞台全体で受けています。

e.stageX / e.stageY は「ステージ座標」です。ここが CreateJS の親切なところで、

  index.html:103
    width: min(1500px, 98vw, calc((100vh - 190px) * 13 / 7));

このように canvas は CSS で拡大縮小されていますが、
CreateJS は表示サイズと実際のサイズ(1300×700)の比率を自動で換算して、
**常に 1300×700 の座標系で** e.stageX を返します。

だからフルスクリーンにしても大砲の狙いはずれません。
自分で canvas.getBoundingClientRect() を使って換算する必要はありません。

右クリックだけは CreateJS ではなく素の DOM で受けています。

  js/main.js:424-428
    document.getElementById("gameCanvas").addEventListener("contextmenu", function (e) {
      e.preventDefault();
      if (PP.editor && PP.editor.active) return;
      PP.cannon.swap();
    });

e.preventDefault() でブラウザのコンテキストメニューを止めています。
これをしないと右クリックのたびにメニューが出て、ゲームになりません。

また stagemousedown 側でも右ボタンを弾いています。

  js/main.js:324
    if (e.nativeEvent && e.nativeEvent.button === 2) return;   // 右ボタンは交換専用

e.nativeEvent は「CreateJS が包む前の、生の DOM イベント」です。
button === 2 が右ボタンを意味します。


## 2-10 Text と Shadow

  js/fx.js:130-133
    var t = new createjs.Text(str, "700 " + (size || 18) + 'px "Cinzel",...', color);
    t.textAlign = "center"; t.textBaseline = "middle";
    t.x = x; t.y = y;
    t.shadow = new createjs.Shadow("rgba(0,0,0,0.85)", 0, 2, 4);

Text は文字を表示するオブジェクトです。フォント指定は CSS の font 属性と同じ書式。
textAlign = "center", textBaseline = "middle" で、(x, y) が文字の中心になります。

Shadow(色, オフセットX, オフセットY, ぼかし)は影です。
暗い背景に色付きの文字を出すとき、黒い影を敷くと格段に読みやすくなります。

なお、絵文字(💎 など)も Text で出しています。

  js/ball.js:209-212
    var gem = new createjs.Text("💎", (R) + "px serif");
    gem.textAlign = "center";
    gem.textBaseline = "middle";
    gem.cache(-R, -R, R * 2, R * 2);

絵文字は OS のカラーフォントで描かれるので、実質「無料の画像素材」です。
ここでも cache して、毎フレームのグリフ整形を避けています。


## 2-11 compositeOperation — 加算合成

  js/fx.js:17
    s.compositeOperation = "lighter";

compositeOperation は canvas の合成モードで、"lighter" は **加算合成** です。
下にある色に、自分の色を足し算します。重なるほど明るく、白に近づきます。

光・炎・きらめきの表現に使います。普通の描画(source-over)だと
「上の色で塗りつぶす」ので、光っている感じになりません。

このゲームでは fx.js のリング衝撃波・フラッシュ・きらめきと、
ball.js のフレネル(縁の発光)で使われています。

  js/ball.js:78-79
    fres.compositeOperation = "lighter";
    fres.alpha = 0.5;

ここが巧妙で、fres は base コンテナの子として cache されます。
コンテナを cache するとき、CreateJS は子の alpha と compositeOperation を
反映して焼き込みます。つまり **加算合成の計算が焼き込み時に1回だけ** 行われ、
毎フレームの加算合成のコストがゼロになります(js/ball.js:29-34 のコメント)。


## 2-12 この章のまとめ

  Stage       canvas を管理する舞台。stage.update() で描画
  Container   物をまとめる箱。addChild の順が重なり順
  Shape       Graphics 命令で図形を描くオブジェクト
  Bitmap      画像(または cache した canvas)を貼るオブジェクト
  Text        文字。絵文字も出せる
  Graphics    beginFill → draw… の順。メソッドチェーン
  Ticker      RAF で毎フレーム関数を呼ぶ。e.delta が経過ミリ秒
  Tween       時間指定のアニメーション。to().to().call() で数珠つなぎ
  cache       ベクタ描画を画像に焼いて使い回す。最重要の最適化
  regX/regY   自分のどこを基準点にするか
  mouseEnabled 当たり判定から除外して軽くする
  compositeOperation "lighter" で加算合成 = 光の表現

次の章から、いよいよゲーム本体のコードに入ります。
